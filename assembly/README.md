# Assembly inspection

Listings are generated by `scripts/asm.sh` with Apple Clang 21
(`-std=c++20 -mcpu=apple-m4`, `-O2` unless noted). Regenerate them after any
source change. The snippets below are copied from these files.

| File | Contents |
|---|---|
| `aes_ref_O2.s` | textbook implementation |
| `aes_ttable_O2.s`, `aes_ttable_O0.s` | T-table implementation |
| `aes_ct_O2.s` | constant-time software implementation |
| `aes_armv8_O2.s` | ARMv8 Crypto Extensions implementation |
| `controls_O2.s`, `controls_O0.s` | positive control, its twin, and the workload |
| `openssl_symbols.txt` | hardware-instruction counts and AES symbols in `libcrypto.3.dylib` |

## 1. `ref` and `ttable`: secret-indexed loads are present

The table lookups survive as loads whose **address depends on secret data**.

`ref` (`SubBytes`): **32** register-indexed byte loads, for example:

```asm
ldrb    w9, [x8, x9]          ; x8 = &SBOX, x9 = state byte  ->  S[state byte]
```

`ttable` (rounds 1–9 and the final round): **32** register-indexed word loads, for example:

```asm
ldr     w9,  [x14, w9,  uxtw #2]   ; T0[byte]   (index scaled by 4 bytes)
ldr     w10, [x1,  w10, uxtw #2]   ; T1[byte]
```

Each index is a byte of the AES state, which depends on the key and the
plaintext. Which cache line is touched therefore depends on secret data:
the property exploited by cache-timing attacks.

## 2. `ct`: no secret-indexed loads, no secret-dependent branches

- The S-box function `sbox8` (8 S-box evaluations in parallel) is **917
  straight-line instructions with 0 branches and 0 register-indexed loads**.
  It uses only `and`, `eor`, `lsl`, `lsr`, `sub`, and `mul`.
- `encrypt_block` contains exactly two conditional branches:
  - `b.ne LBB4_1`: the round loop (counter `w22`, fixed at 9 iterations, independent of data).
  - `b.ne LBB4_4`: the stack-protector check.
- **Compiler transformation:** the source computes a byte mask as
  `(b & 0x0101…) * 0xFF`. Clang replaced that multiplication with
  shift-and-subtract (`lsl x9, x8, #8; sub x9, x9, x8`), which has the same
  value and is still branch-free. The `xtime` reduction `* 0x1B` remains a
  `mul` (77 `mul` instructions in `sbox8`).
- **Caveat:** this shows the absence of branches and table lookups. It does
  not prove constant-time execution. That still depends on every instruction
  used (for example `mul`) having data-independent latency, which Apple ties
  to the DIT (Data Independent Timing) bit.

## 3. `armv8`: hardware AES instructions are used

`aes_armv8_O2.s` contains **60 `aese` and 54 `aesmc`** instructions
(single-block path plus the 4-way unrolled bulk path):

```asm
aese    v0.16b, v1.16b        ; AddRoundKey + SubBytes + ShiftRows
aesmc   v0.16b, v0.16b        ; MixColumns
```

The S-box lives inside the execution unit, so there is no memory lookup.

## 4. Positive control: the injected branch at `-O0` and `-O2`

**`-O2`:** the source `if (s < 0x80)` became a single *test-bit-and-branch*
on bit 7, followed by a tail call:

```asm
__ZN3aes10leaky_gateEh:
    tbnz    w0, #7, LBB1_2               ; s >= 0x80 ? skip the work
    b       __ZN3aes16control_workloadEh ; s <  0x80 : tail-call the workload
LBB1_2:
    ret
```

The branch was **not** converted into a branch-free `csel`. The workload is a
loop of 64 dependent multiply-adds, which the compiler cannot evaluate
speculatively. So the intended secret-dependent branch survives optimisation.

**`-O0`:** the same branch appears as a compare-and-branch through the stack:

```asm
    sturb   w0, [x29, #-5]
    ldurb   w8, [x29, #-5]
    subs    w8, w8, #128
    b.ge    LBB1_2
```

**Twin (`-O2`):** branch-free selection with a mask:

```asm
    bl      __ZN3aes16control_workloadEh   ; always do the work
    bic     w8, w0, w20, asr #31           ; keep the result if s < 0x80
    neg     w9, w19, lsr #7
    and     w9, w9, w19
    orr     w0, w8, w9                     ; ...otherwise keep s
```

**Workload (`-O2`):** fixed trip count, no data-dependent control flow:

```asm
    mov     w8, #0x40                      ; 64 iterations
1:  madd    w0, w0, w9, w10                ; x = x * 1664525 + 1013904223
    subs    w8, w8, #1
    b.ne    1b
```

## 5. OpenSSL: which code path actually runs

`libcrypto.3.dylib` (OpenSSL 3.6.1) contains **4,190 `aese`** and **3,631
`aesmc`** instructions, and three families of AES code (see
`openssl_symbols.txt`):

- `aes_v8_*`: ARMv8 hardware instructions.
- `vpaes_*`: vector-permute AES (Hamburg 2009).
- `bsaes_*`: bit-sliced AES.

A portable C implementation (`AES_encrypt`) is also present.

The selected routine was verified with debugger breakpoints:

| Environment | Routine hit | Measured latency |
|---|---|---|
| default | `aes_v8_ecb_encrypt` (hardware) | ≈ 8.7 ns/block |
| `OPENSSL_armcap=0` | `AES_encrypt` (portable C) | ≈ 35 ns/block |

Disabling capability detection does not select `vpaes`. It falls all the way
back to the portable C routine, whose speed is close to our own T-table
implementation. The leakage of that path is measured in the `armcap0` sub-run.

## 6. Harness loop

The timed loop in `time_batch` keeps every `encrypt_block` call (a virtual
call that cannot be removed), and `clobber_memory()` forces each result to be
stored. The timer reads are surrounded by `isb` barriers.
